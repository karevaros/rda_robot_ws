# 수확한 열매를 장면에서 없애기 (2026-07-29)

실제 수확에서는 **딴 열매가 사라진다** → 그 뒤에 가려져 있던 열매가 보이고, 진입로도 열린다.
그런데 코드는 딴 열매를 그대로 두고 있었다. 그래서 "수확 가능 열매 N개" 는 **한 프레임 정지 장면
기준의 하한값**이었다. 이 문서는 그걸 실제 수확 런처럼 바꾼 내용이다.

## 1. 고치기 전 상태 (실측 확인)

| 층위 | 문제 |
|---|---|
| 계획(planning scene) | `_play_cycle` 이 파지 후에도 열매를 장면에서 빼지 않는다 |
| 재발행 | `obstacle_publisher` 가 **1초마다 전체 재발행**(`period=1.0`) → 지워도 곧 되살아난다 |
| 목록 | `run_harvest_all` 이 수확 가능 목록을 **시작할 때 한 번만** 뽑는다 → 새로 열리는 열매가 후보에 못 들어옴 |
| 인지 | Gazebo 에서 열매가 그대로라 카메라가 계속 본다 → 뒤쪽 열매의 가림이 안 풀림 |

**⚠ 그리고 애초에 열매는 충돌객체가 아니었다.** `obstacle_publisher` 는 `kind: target` 을
CollisionObject 발행에서 제외한다("목표를 장애물로 세면 계획 실패"). 그런데 이 규칙은 **목표가
아닌 이웃 열매까지 전부** 빼버린다 → 이웃 열매를 밀고 지나가는 궤적이 충돌로 잡히지 않는다.

## 2. 바꾼 것

### 열매도 장애물로 (`publish_targets`, obstacle_publisher)

`publish_targets:=true` 면 `kind: target` 도 CollisionObject 로 발행한다. **목표 열매 자신은
구 영역 ACM 이 허용**하므로(반경 ρ 안, `region_max_object` 이하 크기) 계획이 막히지 않고,
이웃 열매만 장애물로 남는다.

- 실측: 켜면 손가락·손바닥이 이웃 열매를 관통하는 궤적이 바로 잡힌다
  (`rg2_leftfinger|fruit_r0_p2_t0_f2×4`, `rg2_hand|…×3`).
- 실측: 수확 가능 열매가 **6 → 4 개**로 준다(원래 6개는 이웃 열매를 무시하고 센 값이었다).
- 기본값은 `false`(기존 측정 기준선 유지). 켜고 재는 것이 '진짜' 기준이다.

### 수확 → 제거 (`harvest_remove`, pregrasp_demo)

`_remove_fruit(name)` 이 **세 곳을 함께** 처리한다. 하나라도 빠지면 조용히 되살아난다.

1. `/harvested` 토픽으로 이름 발행 → `obstacle_publisher` 가 **재발행 제외 목록**에 넣고 REMOVE 발행
   (TRANSIENT_LOCAL 이라 구독이 늦게 붙어도 놓치지 않는다)
2. planning scene 에 즉시 `CollisionObject.REMOVE`(재발행 주기를 기다리지 않게)
3. Gazebo `/delete_entity` 로 모델 삭제 — 열매가 각각 독립 모델(`<model name="fruit_…">`)이라 가능.
   시뮬 미구동이면 서비스가 없어 조용히 건너뛴다.

`reset`(또는 `*`)을 `/harvested` 로 보내면 제외 목록이 비워진다(재생 데모 반복용).
단 **Gazebo 에서 실제로 지운 뒤에는 원복하지 않는다**(되살릴 수 없다 → 시뮬 재시작 필요).

### 매 수확 후 목록 재도출 (`run_harvest_all`)

시작할 때 한 번 뽑아 두고 도는 대신, **수확할 때마다 수확 가능 목록을 다시 뽑는다.**
새로 열린 열매가 그 시점부터 후보가 된다. 실패한 열매는 `failed` 에 넣어 무한 재시도를 막는다.
끝나면 **수확 가능 열매 수 추이**를 로그로 남긴다 — 이게 "앞을 따면 뒤가 열린다" 의 실측 근거다.

### 도달 판정 기준 통일 (07-28 기록의 2순위 항목)

`_select_reachable` · `_is_harvestable` · `run_harvest_all` · 인터랙티브 모드가 모두
**수확 작업공간(구 영역)을 허용한 뒤** IK 를 본다. 예전엔 판정만 허용 전에 해서
'목록엔 있는데 계획에선 도달불가' 가 생겼다(실측: 도달 3개 → 6개).
비용을 아끼려고 **2단계**로 본다 — 허용 없이 통과하면 그대로 통과, 실패한 것만 구 영역을 걸고 재판정.

## 3. 검증 (설계값 장면, 재생 모드)

```bash
ros2 launch rda_robot_moveit_config pregrasp_demo.launch.py \
  harvest_all:=true harvest_max:=3 loop:=false rviz:=false publish_targets:=true
```

```
수확 가능 열매 4 / 전체 74 (워크스페이스 필터)
── 수확 1: fruit_r0_p3_t0_f0 …   수확 완료 → 장면에서 제거 (누적 1개)
수확 가능 열매 4 / 전체 73
── 수확 2: fruit_r0_p3_t0_f2 …   수확 완료 → 장면에서 제거 (누적 2개)
수확 가능 열매 3 / 전체 72
── 수확 3: fruit_r0_p2_t0_f0 …   수확 완료 → 장면에서 제거 (누적 3개)
수확 가능 열매 2 / 전체 71
연속 수확 완료 — 수확 3 / 시도 3 / 건너뜀 0
  수확 가능 열매 수 추이(수확할 때마다 재도출): 4 → 4 → 3 → 2
```

- 제거는 매번 반영된다(전체 74 → 73 → 72 → 71).
- 첫 수확 뒤 **4 → 4**: 하나를 땄는데 수가 그대로 = **새로 하나가 열렸다**(막고 있던 열매가 빠져서).
- 이후로는 새로 열리는 것 없이 줄어든다(3 → 2).

⚠ **이 장면에서는 '막힘' 효과만 측정된다.** 목표를 yaml 설계값에서 읽으므로 **가림(occlusion) 효과는
없다.** 진짜 이득은 인지 장면이다 → §4.

## 4. 인지 장면 검증 (Gazebo) — **성공**

```bash
ros2 launch rda_robot_moveit_config perception_demo.launch.py execute:=true run_demo:=true \
  harvest_all:=true harvest_max:=3 harvest_remove:=true loop:=false gui:=false rviz:=false \
  sensors:=d435i world:=greenhouse detect:=true      # region_margin 기본 0.13
```

```
파지 거리 자동유도 — 손가락 패드 깊이 9.0~21.2cm · grasp_depth=0.33 → grasp_offset 13.1cm
옥토맵 안정화 대기 완료(197305B) → 이제 기준선을 잡는다
인지 열매 19개 수신 (2.0s, 개수 안정화 후)
── 수확 1: det_13 → ② 직선 Cartesian 8점(fraction=1.00, 관절 0.44rad)
   det_13 → Gazebo 모델 fruit_r0_p3_t0_f0 (거리 0.7cm, 2등 5.4cm) · 삭제
── 수확 2: det_17 → 직선 1.00, 0.47rad → fruit_r0_p2_t0_f0 삭제
── 수확 3: det_14 → OMPL 회피 8점        → fruit_r0_p3_t0_f2 삭제
연속 수확 완료 — 수확 3 / 시도 3 / 건너뜀 0     (인지 열매 19 → 16)
```

**성립한 것**: 인지(옥토맵) 장면에서 검출 → 수확가능 판정 → 계획 → 컨트롤러 실구동 →
**Gazebo 모델 삭제 → 인지 결과에서 사라짐 → 다음 라운드 재도출** 이 한 바퀴 돈다.

**아직 안 보이는 것**: 수확가능 추이는 **2 → 2 → 1 → 0** 으로, "뒤 열매가 새로 열린다" 는
이 표본에서는 안 나타났다. 이유 두 가지:
- 판정이 **확률적**이다 — 같은 옥토맵(195.7KB)에서 연속 두 번 재도출한 값이 1↔5 로 흔들린다
  (KDL IK 가 무작위 재시작, `ik_timeout=0.5`). 이 잡음이 '열린 열매 1~2개' 신호보다 크다.
- 도달권이 좁다 — 19개 중 13개가 기하 프리필터에서 걸린다(팔 reach 0.93m).
⇒ **다음**: 판정을 반복(또는 `ik_timeout` 상향)해 잡음을 줄인 뒤, base 를 옮겨 표본을 넓혀 재측정.

### 🔴 이 검증에서 드러난 가장 중요한 것 — ρ 기본값이 센싱 장면에 맞지 않았다

옥토맵 안정화를 넣기 전에는 **수확 1회 성공**했는데, 그건 **지도가 비어 있을 때** 계획한 것이라
무효였다. 지도를 다 쌓고 재니 **수확 0 / 후보 4개 전부 `solve_pregrasp` 실패**.

원인은 구 영역 반경이다. 설계값 장면 기본 `region_margin=0.03`(ρ≈6.5cm)은 **그리퍼 점유공간을
못 덮는다** — 손가락이 tcp 기준 21cm 까지 뻗으므로 열매 뒤 옥토맵에 걸린다.
Stage 5 가 이미 **센싱 장면 최소 ρ=15.7cm** 를 실측해 뒀는데 그 값이 launch 로 이어지지 않았다.
→ `perception_demo` 에 `region_margin` 인자 추가, **기본 0.13**(ρ≈16.5cm). 그 뒤 수확 3/3 성공.

⇒ **접근 축 캡슐/원뿔이 필요한 진짜 자리가 여기다.** 지금은 그리퍼를 덮으려고 구를 16.5cm 로
키웠고, 그 구는 이웃 열매·화방대를 통째로 허용한다. 접근축 방향으로만 긴 캡슐이면 같은 그리퍼
공간을 훨씬 좁은 부피로 덮는다.

## 4-1. 검증 과정에서 고친 것들

여기서 **세 가지 결함이 잡혔고 고쳤다.**

### ① 인지 타깃 이름은 Gazebo 모델 이름이 아니다 (삭제가 아예 안 됐다)

```
Gazebo 모델 삭제 실패: det_17 (Entity [det_17] does not exist)
```

인지 타깃은 `det_N`(번호표)이고 Gazebo 모델은 `fruit_r0_p2_t0_f1`(yaml 이름)이다.
→ `_gazebo_name()` 이 **위치로 매칭**한다(시뮬 월드가 `obstacles.yaml` 에서 생성되므로 가능).
허용 오차 `harvest_match_tol`(기본 6cm)이고, **2등과 2cm 이상 벌어져야** 채택한다 —
한 화방 열매는 6cm 간격이라 모호하면 **엉뚱한 열매를 지우는 조용한 오류**가 된다.
실측 매칭: 최근접 0.7~1.3cm vs 2등 5.0~5.4cm → 안전하게 갈린다. 수정 후 삭제 성공,
인지 열매 19 → 18개로 즉시 반영됐다.
※ 실물에서는 딴 열매가 물리적으로 사라지므로 이 매칭 자체가 필요 없다(시뮬 전용 보정).

### ② 검출이 다 쌓이기 전에 데모가 시작했다

첫 메시지를 받자마자 시작해 **검출 3개**로 목록을 만들었다(30초 뒤엔 19개).
→ `_perception_targets` 가 **개수가 안정될 때까지**(3회 연속 동일) 기다린다.
`perception_demo` 는 `targets_wait:=60`.

### ③ 🔴 옥토맵이 비어 있는 동안 잰 기준선 (가장 중요)

수정 ①②를 하고도 **수확가능 4 → 0** 이 나왔다. 계측을 넣어 보니 원인이 수확이 아니었다:

| 라운드 | 수확가능 | 탈락 사유 | 옥토맵 |
|---|---|---|---|
| 수확 전 | 4/18 | 기하 14 (IK 탈락 0) | **없음(0B)** |
| 수확 후 | 0/17 | 기하 14 · grasp IK 4 · pre IK 2 | **364KB** |

즉 **지도가 아직 안 쌓인 동안 전부 '수확 가능'으로 잡혔고**, 그 뒤 지도가 자라면서 후보가
사라진 것이다. 이걸 '수확해서 줄었다'로 읽으면 정반대 결론이 된다.
→ `run_harvest_all` 이 센싱 장면에서 **옥토맵 안정화(`_wait_octomap_stable`) 후 기준선**을 잡는다.
→ `_harvestable_targets` 가 **탈락 사유(기하/pre IK/grasp IK)와 옥토맵 크기**를 매 라운드 남긴다.

**교훈**: 센싱 장면의 '가능/불가능' 판정은 **지도가 안정된 뒤**에 재야 한다. 안 그러면
빈 지도 위의 낙관적 값과 채워진 지도 위의 값을 비교하게 된다.

## 5. 파지 거리를 그리퍼에서 유도 (2026-07-29, 사용자 지적)

> "수확 시 엔드이펙터의 길이를 고려하지 않고 툴센터 기준으로 동작한다."

`grasp_offset`(파지 시 TCP 가 열매 중심 앞에 멈추는 거리)이 **상수**였다(0.13m).
그리퍼를 바꾸면 조용히 틀린다 — 손가락이 짧은 그리퍼면 열매가 **손끝 너머**에 놓여
빈손으로 닫히고, 손목이 열매를 들이받는다.

→ `RI.gripper_span()` 이 **손가락 링크 기하를 tcp 프레임으로 옮겨 접근축에 투영**해 실제 패드
깊이를 잰다. `grasp_offset_auto`(기본 true) + `grasp_depth`(0=패드 입구·1=손끝, **기본 0.33**).

| | 값 |
|---|---|
| RG2 패드 깊이(tcp 기준, 접근축 투영) | **9.1 ~ 21.3 cm** |
| 종전 상수 | 13.0 cm (그리퍼가 바뀌어도 안 따라간다) |
| 자동유도 `grasp_depth=0.33`(기본) | **13.1 cm** — 종전과 같은 위치, 검증된 동작 유지 |
| 자동유도 `grasp_depth=0.5` | 15.2 cm = 패드 중앙(파지 안정성은 낫다) |

- 🔴 **깊이는 공짜가 아니다.** 0.5 로 두면 손끝이 열매 중심 **뒤 6.1cm** 까지 들어가야 하는데,
  센싱 장면에서는 그 공간이 막혀 **파지 자세가 아예 안 나왔다**(실측: 수확 1 → 0, 후보 4개 전부
  `solve_pregrasp` 실패). → 기본은 0.33, 트인 곳에서는 인자로 올릴 것.
- 설계값 장면 실측(0.33): 수확가능 5개 · 연속수확 2/2 성공. 인지 장면: 수확 3/3(§4).
- ⚠ **control 모드 URDF 는 로봇 링크 collision 이 없다**(Gazebo 물리 접촉 회피용) → collision 만
  보면 손끝 깊이를 못 잰다(실측 10.5~10.5cm). `link_geoms` 가 **visual 로 폴백**한다.
- SRDF 가 낡아 그리퍼 관절 이름이 안 맞으면 **URDF 서브트리 폴백**(tcp 아래 움직이는 관절)을 쓴다.
- 🔴 **건전성 가드**: 손가락이 접근축 방향으로 뻗지 않으면(깊이가 **0 대칭**으로 나오면 — 실측
  Robotiq 2F-85 에서 −7.4~+7.4cm, 즉 옆으로 잰 것) **자동유도를 버리고 상수를 유지**하며 경고한다.
  그대로 썼으면 파지점이 TCP 원점(0cm)이 돼 손목으로 열매를 들이받았을 것이다.
  ⇒ 그리퍼를 바꾸면 **`gen_srdf.py` 재실행이 여전히 필수**(접근축·그리퍼 그룹이 SRDF 에 묶임).

## 6. 함정 기록

- **측정/데모 스택을 두 개 띄우지 말 것.** 같은 DDS 도메인에서 move_group·obstacle_publisher 가
  둘 뜨면 장면이 섞인다. 실제로 `publish_targets:=true` 로 돌던 다른 창의 발행이 비교 측정에
  섞여 들어와 접촉이 4건 잡혔다(그 실행은 폐기하고 재측정했다).
- `harvest_all` + `loop:=true` 는 다 따고 나면 장면을 원복해 반복한다. Gazebo 삭제를 한 경우엔
  원복하지 않으므로 반복 데모는 `harvest_remove:=false` 나 시뮬 재시작이 필요하다.
