### 🔴 CAP-12 를 비교컷으로 쓸 수 있는 이유 (조건 통제)
**같은 창·같은 카메라에서 파라미터만 바꿔** 연속으로 찍었다. RViz 를 띄운 채
`crop_tuner` 와 같은 저장 경로(`write_values`)로 `rachis_z_frac` 과 `pedicel_radius` 만
바꾸고, 퍼블리셔의 라이브 리로드(실측 187 ↔ 240개)를 기다렸다 촬영했다.
⇒ 두 컷의 **차이는 오직 그 두 파라미터**다.
· 왼쪽(종전) `rachis_z_frac=0.0` · `pedicel_radius=0.0` — 화방대가 **클러스터 중심**으로 가
  열매 속을 관통한다.
· 오른쪽(교정) `rachis_z_frac=1.0` · `pedicel_radius=0.002` — 화방대가 **열매 윗면**을 지나고
  각 열매가 **소과경**으로 매달린다.
⚠ 2026-08-18 에 "자세가 달라 비교컷으로 쓰면 안 되는" 2컷을 남긴 적이 있다(근거대장 6-4-3).
  이번 컷은 그 실수를 피하려고 **카메라를 건드리지 않은 채** 파라미터만 바꿨다.

### ⚠ 이 컷들이 보여 주지 **않는** 것
· **잎이 없다**(사용자 지시로 제외). 사진(`tomatopick/`)에는 잎이 무성하지만 모델에는 없다.
  ⇒ 이 그림으로 "캐노피를 재현했다"고 쓰면 안 된다. 회피 비교 해석에 직접 영향
  (`docs/구성프리셋-선정규칙.md` 4장).
· **꽃받침(calyx)이 없다.** 그리퍼가 파지할 때 실제로 닿는 부위다.
· **치수는 사진에서 잰 값이 아니다.** 사진에 스케일 기준이 없어 비율조차 신뢰할 수 없었다.
  사진이 정한 것은 **구조**뿐이고, 절대 치수는 기존 근거(AIHub·STEP 실측)와 통상값이다.
· 화방대 **처짐(droop)은 없다** — 축을 열매 윗면에 얹으면 처지는 순간 열매를 파고든다
  (실측: 처짐 3cm 에서 1.3cm 침투).

## 🔴 관리 세션이 알아야 할 것 3가지

### ① CAP-06 은 요청서의 전제와 실제 설계가 다르다
요청서: *"직선이 주 줄기에 막혀 **OMPL이 우회**하는 궤적"*.
그러나 이 시스템은 **접근 구간에서 우회하지 않는다** — 6주차에 정한 구간별 정책이
*"직선 접근은 재계획하지 않는다(곧게 들어가는 게 정의 · 바꾸면 파지 기하가 깨진다)"* 이기 때문이다.
줄기를 피하는 실제 기전은 **접근각 탐색**이다: 여러 (φ, θ) 조합을 시험해 줄기에 막히지 않는
각도를 고르고, 그 각도로 **직선** 진입한다(5주차 ablation: 완전직선 **2/12 → 11/12**).
· 이 컷의 조건: `pregrasp_demo.launch.py loop:=true rviz:=true` · 채택 로그
  **`직선접근 각도 채택: φ=-40° θ=+30° → 직선 Cartesian fraction=1.00 · 접근구간 관절 0.39 rad`**
· ⇒ 슬라이드 설명을 **"OMPL 우회"가 아니라 "접근각 탐색 후 직선 진입"** 으로 쓸 것.
  ("우회"는 home→pre-grasp 구간에서 일어나며, 그 구간은 CAP-05 에 담겨 있다.)

### ② CAP-11 은 재촬영했다(2026-08-18) — 규격 충족
종전 컷(08-16, 1500px)을 버리고 **주입 런을 다시 돌려 새로 찍었다**. 1833×1310.
* **실행 조건**: `perception_demo.launch.py execute:=true run_demo:=true harvest_all:=true
  harvest_max:=3 harvest_remove:=true gui:=true rviz:=true sensors:=d435i world:=greenhouse
  detect:=true` + `inject_obstacle.py --thresh 0.02 --delay 0.3`
* **발화 실측**(이 컷의 진짜 근거 — 그림이 아니라 로그다):
  `실행 중 장면 변화 감지 — 남은 11점 중 1점이 막혔다(진행 22%) · 접촉:
  replan_test_block|grasped_det_13, link3|replan_test_block, link4|replan_test_block`
  → `실제 자세 동기화 — 가정했던 자세와 최대 **0.932 rad** 차이`
  → `[det_13 ④home] 재계획 1/2` → **`수확 사이클 완료`**(재계획 후 완주)
* **캡처 시점**: 트리거 발화 **+3.1초**(발화 `…056.82` ↔ 캡처 `…059.89`). 2.2초 간격으로
  16프레임을 찍어 타임스탬프로 골랐다.
* ⚠ **주입한 상자는 화면에 눈에 띄게 그려지지 않는다**(이 RViz 설정). 그림이 보여 주는 것은
  **발화 순간의 장면**(옥토맵·검출 열매·뻗은 팔)이고, *무엇이 막았는지*는 위 접촉 쌍이 말한다.
* ⚠ **같은 조건에서 결과가 갈렸다** — 직전 런(같은 날)은 `재계획 실패(계획 자체가 안 나온다) → 포기`
  였고, 이 런은 완주했다. **재계획 성공은 보장되지 않는다**고 적어야 한다.

### ③ 요청서의 수치 하나가 틀렸다 — "온실 월드(오브젝트 188)"
**188 = 온실 186 + `ground_plane` + `rda_robot`** 이다. 온실 오브젝트 자체는 **186**.

| CAP-15 | `cap15_crop_tuner.png` | 1700×1500 | 작물 튜너 GUI 단독 · **슬라이더 19개 전부 한 화면** | ✅ (가로 1700px) |

**촬영 조건**
```bash
ros2 run rda_robot_bringup crop_tuner.py          # 인자 없음 = 정본 config/obstacles.yaml
python3 docs/scripts/capture_window.py --name "작물 파라미터 튜너" \
        --move 120,60 --size 1700x1500 --settle 3 --out <파일>
```
· 창 크기를 **1700×1500** 으로 준 이유: 기본 창(532×640)은 슬라이더가 **15개까지만** 보이고
  나머지 4개(화방대 마디 수·소과경 굵기·소과경 최소 길이·주간 간격)가 스크롤 아래로 숨는다.
  실제로 1700×1150 으로 먼저 찍었다가 4개가 잘려 다시 찍었고, 1700×1330 은 마지막 1개
  (주간 간격)가 잘렸다. ⇒ **"슬라이더 19개"를 근거로 쓰려면 이 크기여야 한다.**
· 아래쪽 여백은 스크롤 영역 안이라 **자르지 않았다**(패널 테두리를 깨지 않기 위해).

**슬라이더 19개 실측**(화면 순서) — 줄기 반경·줄기 높이·줄기 곡선 편차·줄기 곡률·줄기 마디 수 ·
첫 화방 높이·화방 수직간격·주당 화방 수·화방당 열매 수·열매 반경·클러스터 거리·뭉침 정도 ·
화방대 굵기·화방대 높이·화방대 처짐·화방대 마디 수·소과경 굵기·소과경 최소 길이·주간 간격.
⇒ 관리 문서의 **"13개"는 08-21 이전 값**이고 **19개가 맞다**(08-21 작물 모델 교정으로 6개 추가).

### ⚠ 이 컷을 인용할 때
· **화면의 값은 정본 `obstacles.yaml` 그대로**다 — `첫 화방 높이 0.100`(현실값 0.35 아님 ·
  도달권 때문에 낮춰 둔 값) · `화방대 높이 0.000`·`소과경 굵기 0.000`(상세 형상 키의 **중립
  기본값** — 상세 장면은 `robot_config:=detail` 프리셋이 켠다). **이 화면을 "현실 배치"로
  읽으면 안 된다.**
· **값을 바꾸지 않았다** — 촬영 전후 정본 md5 `19892537b86e4dd86294e1d535c2ce35` 동일.
· 튜너는 값을 바꾸는 **순간 파일에 저장**한다(되돌리기 없음). 캡처 목적으로 열 때는
  슬라이더를 건드리지 말 것.
· CAP-04(`cap04_crop.png`)는 RViz+튜너 **합성**이라 성격이 다르다 — 이 컷은 **단독·슬라이더 확대**.
