### 6-3-2. Unity ↔ ROS 연동 (2026-08-16, 사용자 지시) — **살아 있는 ROS 자세를 Unity 가 재현**

**무엇인가 / 무엇이 아닌가** — 이것은 **미러(재현)** 다. Gazebo/ros2_control 이 물리와 제어를

주는 것이 아니다**(그건 하드웨어 인터페이스 교체 = 별개 작업). 보고서에 "Unity 로 시뮬레이션

**구성** — ROS 쪽 `ros_tcp_endpoint`(Apache-2.0) ↔ Unity 쪽 ROS-TCP-Connector v0.7.0 +

않아도 검증된다(Editor tar.xz 에 `LinuxStandaloneSupport` 가 들어 있어 가능했다).

```bash

ros2 launch rda_robot_moveit_config perception_demo.launch.py execute:=true …
ros2 run ros_tcp_endpoint default_server_endpoint --ros-args -p ROS_IP:=0.0.0.0 -p ROS_TCP_PORT:=10000
python3 docs/scripts/test_unity_ros_bridge.py
```

⚠ **이 검증이 보증하지 않는 것** — **Unity 의 물리 거동은 여전히 미검증**이다. 미러라서

### 6-6. 🟢 Unity 물리 거동 시험 (2026-08-18 신설) — **유도 effort 값의 첫 실전 시험**

**왜 필요했나.** 3종 어디에서도 **중력에서의 팔 거동을 확인한 적이 없었다**:
Gazebo 는 control 모드에서 로봇 링크 중력 OFF·collision 제거 · Unity 미러는 중력 OFF·콜라이더 OFF ·
Isaac 은 범위 밖. ⇒ 2026-07-30 에 URDF 질량·관성에서 유도한 effort 값이 **실제로 팔을 버티는지**가
미검증 부채로 남아 있었다(`후속과제.md` 🔴 표). 이 시험이 그 한 가지에 답한다.

```bash
ros2 run rda_robot_bringup gen_unity_assets.py --out ~/robot_ws/export/unity
~/unity/Editor/Unity -batchmode -nographics -quit -projectPath ~/robot_ws/export/unity \
  -executeMethod RdaBatch.BuildPhysicsScene      # 이어서 RdaBatch.BuildPhysicsPlayer
python3 src/docs/scripts/test_unity_physics.py --project ~/robot_ws/export/unity
```

**측정 조건**(작성지침 5장 — 조건 없는 수치 금지):
중력 **ON** · 로봇 콜라이더 **OFF** · fixed dt **0.02 s** · stiffness **1e5** / damping **1e4** ·
정착 **6 s** · 목표 자세로 관절을 순간 세팅한 뒤 드라이브 목표도 같은 값.

| 검사 | 값 | 재확인 |
|---|---|---|
| 검증 통과 | **8 / 8** | ✅ 2026-08-18 |
| home(전부 0) | 최대 드리프트 **0.00596 rad** · tcp 이동 **1.6 mm** | ✅ |
| **수평 전개(최악 자세)** | 최대 드리프트 **0.07311 rad**(4.2°) · tcp 이동 **78.9 mm** | ✅ |
| 수평 + 팔꿈치 굽힘 | 최대 드리프트 **0.02735 rad** · tcp 이동 **13.4 mm** | ✅ |
| 수확 유사 자세 | 최대 드리프트 **0.00213 rad** · tcp 이동 **2.4 mm** | ✅ |
| **대조 — 종전 플레이스홀더 10 Nm** | 최대 드리프트 **0.69404 rad**(39.8°) · tcp 이동 **825 mm** = **무너진다** | ✅ |
| **대조 — forceLimit 을 10^5 로** | 유도값과 **완전히 동일**(0.07311 rad) | ✅ |
| 원인 귀속 — stiffness 10^7 | tcp 이동 **78.9 → 18.1 mm** | ✅ |

🟢 **결론 — 유도 effort 값은 이 조건에서 충분하다.**
· 종전 플레이스홀더(10 Nm)로는 최악 자세에서 팔이 **무너진다**(825 mm) ⇒ 2026-07-30 의 교체는
  **실측으로 정당화됐다**(그전까지는 계산으로만 정당화돼 있었다).
· forceLimit 을 10^5 로 올려도 결과가 **완전히 같다** ⇒ **유도값에서는 어떤 관절도 토크 상한에
  걸리지 않는다**(상한이 병목이 아니다).
· 최악 자세의 잔여 **78.9 mm** 는 effort 가 아니라 **드라이브 게인** 쪽이다 — stiffness 를 10^7 로
  올리면 18.1 mm 로 줄고, 20초까지 돌려도 79.9 mm 로 **정착**한다(발산이 아니다).

⚠ **이 시험이 보증하지 않는 것**(보고서에 반드시 함께 적는다)
1. **접촉·충돌 응답은 여전히 미검증** — 로봇 콜라이더를 끄고 잰다. 켜면 자기충돌을 PhysX 가
   밀어내며 생기는 오차와 중력 처짐이 섞여 **원인을 가를 수 없다**(2026-08-16 미러에서 실측된 현상).
2. **드라이브 게인은 플레이스홀더** — 잔여 처짐 값은 게인에 따라 달라진다. 이 시험이 답하는 것은
   *"주어진 게인에서 effort 상한이 부족한가"* 이지 *"게인이 옳은가"* 가 아니다.
3. **실기 정확도가 아니다** — PhysX 안의 값이다. effort 값 자체도 여전히 **제조사 정격이 아니라
   유도값**이다(`joint_effort_derive.py`).
4. **Isaac 은 그대로 범위 밖** — 같은 effort 를 쓰지만 PhysX 설정·솔버가 달라 결과가 옮겨지지 않는다.

🔴 **곁에서 드러난 결함 — Unity 임포터의 forceLimit 을 믿으면 안 된다.**
`ArticulationDrive.forceLimit` 을 URDF Importer 가 넣어 준 값으로 쓰려 했더니, **같은 프로젝트에서
실행마다 64(=URDF effort) 로도 0 으로도 읽혔다.** 0 이면 토크 상한이 0 이라 드라이브가 아무 힘도
못 내고, 그 상태로 재면 *"effort 값이 버티는가"* 가 아니라 *"드라이브 없이 떨어지는가"* 를 재게 된다
(첫 측정이 정확히 그랬다 — 겉보기엔 "드리프트 0.055 rad" 로 그럴듯했다).
⇒ 생성기가 `Assets/Resources/joint_effort.json` 을 쓰고 프로브가 **URDF 값을 직접** 넣는다.
⇒ 검사에 *"forceLimit = URDF effort"* 항목을 넣어 **다음에 또 조용히 0 이 되면 실패로 잡는다**.

⚠ **함정 2건 더**(재현 시 볼 것)
· **드라이브 설정은 한 프레임 양보한 뒤에 해야 한다** — `Start` 에서 바로 쓰면 URDF Importer 가
  붙인 컴포넌트가 나중에 초기화되며 `xDrive` 를 통째로 덮어쓴다.
· **두 플레이어를 같은 폴더에 빌드하면 앞 것이 지워진다** — `Build/RdaPhysicsPlayer` 로 빌드했더니
  미러 검증용 `Build/RdaPlayer` 가 통째로 사라졌다 → `Build/physics/` 로 분리했다.
⚠ **생성기 재실행은 프로젝트를 비운다**(`Library` 만 보존) — 씬·플레이어·리포트가 전부 날아간다.
  순서 = 생성 → `BuildPhysicsScene`→`BuildPhysicsPlayer` → `BuildScene`→`BuildPlayer` → `RunAll`.
