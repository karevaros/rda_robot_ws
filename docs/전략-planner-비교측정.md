## 3. 해석

1. **직선접근 구조가 이 장면을 전부 푼다.** `harvest_linear` 는 6열매 전부에서 **완전직선
   (`cartesian(frac=1.00)`) 108/108**, 폴백 0, 플래너 실패 0, **충돌 0**, 유효 **108/108**.
   자유공간 구간(home↔pre-grasp)이 단순해서 어느 planner 를 써도 계획이 성립한다 —
   **planner 선택의 영향이 사실상 없다**(관절길이 중앙값이 6 planner 모두 3.67 rad 로 동일).
2. **`direct` 는 빠르지만 실패가 잦다.** 계획시간 중앙값 1.18s 로 3배 빠른 대신 **폴백 36/108(33%)**,
   plan_to 실패 38회, 유효 72/108(67%). 열매별 편차도 크다(6/18 ~ 18/18) — 자유공간 직행은
   열매가 줄기 사이 깊이 있을수록 잘 안 풀린다.
3. **경로길이는 harvest_linear 이 짧다.** 접근 구간을 왕복으로 세고도 관절 3.67 vs 4.15 rad.
   TCP 길이는 `direct` 가 짧게 나오지만(1.889 vs 1.991 m) 이는 **유효 행만 평균낸 결과**라
   `direct` 의 어려운 사례가 폴백으로 빠져 통계에서 제외된 탓이다 — 성공한 것만 비교한 값이다.
4. **planner 는 `direct` 에서만 갈린다.** 유효율 RRTConnect·PRM 14/18 > EST 13/18 > RRTstar 12/18 >
   RRT 11/18 > BiTRRT 8/18. 호출 단위 실패율도 RRTConnect·PRM 5.6% 가 최저. **RRTstar 는 호출당
   5.04s**(최적화 planner 라 `plan_time` 을 소진) 로 유일하게 계획시간이 두 자릿수(중앙 10.8~13.0s)다.
5. **✅ 안전 기준 재검증 접촉 0건**(07-28 에는 10건). 원인은 **구 영역이 이웃 객체를 통째 허용해서가
   아니라**, TCP 는 직선인데 손목이 뒤집혀 관절이 크게 도는 Cartesian 해였다 — 자세한 규명·수정은
   §6. 실측으로 확인한 것 두 가지:
   - 그 접촉의 상대는 이웃 열매·이웃 화방대가 아니라 **주 줄기**(`rg2_rightfinger|stem_r0_p2_s0`)였다.
   - 문제의 열매에서 구 영역이 실제로 허용한 객체는 **자기 화방대 1개뿐**(`rachis_r0_p2_t0`)이고,
     그건 안전 기준에서도 허용되는 객체다 → 구 영역은 이 접촉과 무관.
6. **⚠ 단, '이웃 열매 통째 허용' 위험 자체는 실재한다 — 이 측정에서 안 보였을 뿐이다.**
   `obstacle_publisher` 가 `kind: target`(열매)을 **충돌객체로 발행하지 않기 때문**에, 이 측정에서는
   이웃 열매가 애초에 장애물이 아니어서 접촉으로 잡히지도 않는다. `publish_targets:=true` 로 켜고
   재보면 **손가락·손바닥이 이웃 열매를 관통하는 궤적**이 즉시 잡힌다(실측:
   `rg2_leftfinger|fruit_r0_p2_t0_f2×4`, `rg2_hand|…×3`). ⇒ **접근 축 캡슐/원뿔 개선의 근거는
   여기**이고, 그 평가는 `publish_targets:=true` 조건에서 해야 한다.

**권고**: 기본값 `strategy:=harvest_linear` 유지. 이 장면에서는 planner 가 결과를 거의 안 바꾸므로
`planner_id` 는 **빠른 것(RRTConnect)** 이면 충분하고, **RRTstar 는 4배 느린 값만 치른다**.
`direct` 를 쓸 경우에는 **RRTConnect·PRM** 이 가장 안정적이다.

## 4. 남은 과제

- **`publish_targets:=true` 조건에서 재측정** — 이웃 열매를 장애물로 세운 '진짜' 기준. 여기서
  구 영역이 이웃 열매를 통째 허용하는 문제가 드러난다(§3.6). 이 조건에서는 수확 가능 열매도
  6 → 4 개로 준다(실측).
- **구 영역 ρ 를 접근 축 캡슐/원뿔로 교체**(§3.6) — 위 조건에서 평가해야 의미가 있다.
- 표본 확대 — 현재 base 위치에서 도달 가능한 6열매. base 를 옮겨가며 재면 표본이 는다.

  연속 수확 런에서는 표본이 자연히 늘어난다.

- 계획 품질 외 **실행 품질**(execute 시 실제 소요시간·추종오차)은 이 측정에 없다.

## 5. 부록 — 1차 측정을 무효로 만든 ACM 버그 (2026-07-28 규명)

측정 내내 `구 영역 ACM 허용(객체 추가 후 재적용) 실패` 경고가 났다. 진단 스크립트로 ACM 을
단계별로 덤프해 **세 가지가 겹쳐 있었음**을 확인했다.

1. **🔴 쌍별(pairwise) entry 가 default entry 를 이긴다.** 객체가 장면에 들어올 때 로봇 링크와의
   쌍별 entry(False)가 만들어지는데, 코드는 `default_entry` 만 True 로 바꾸고 있었다 →
   **목표 화방대 허용이 실제로는 안 걸렸다**('조용한 무효').
   실측: `rachis_r0_p3_t0` default=True 인데 **로봇 링크 17개 전부와 False**. (구 `harvest_zone`
   자신은 쌍별 False 0개라 정상이었다.) ⇒ 이제 허용/차단할 이름의 **행·열을 직접 써넣는다.**
2. **검증 오류 A — `want=False` 인데 '항목 없음'을 불일치로 판정.** MoveIt 은 중복인 False default 를
   저장하지 않는다(실측: `stem_*` 84개가 매번 누락으로 잡혀 4회 재시도를 낭비).
3. **검증 오류 B — 월드 객체끼리의 쌍까지 True 를 요구.** MoveIt 이 검사하는 건 로봇↔월드와
   자기충돌뿐이라 객체끼리의 False 는 정상이다. 작물 106개를 default False 로 깔아두니 구의 쌍별
   행에 그 False 들이 남아 **항상 실패**했고, `_allow_region` 이 False 를 반환해 `_zone_at` 기록까지
   누락됐다(→ `_clear_zone` 무력화).

**수정 효과(같은 3열매 / harvest_linear / RRTConnect)**

| | 수정 전 | 수정 후 |
|---|---|---|
| ACM 경고 | 매 호출 실패 | 0건 |
| 계획시간 | 11.6~12.3s | 2.5~3.6s |
| `fruit_r0_p3_t0_f1` 접근 | 항상 `ompl-avoid`(우회) | `cartesian(frac=1.00)` |
| 도달 가능 열매(표본 선정) | 3개 | 6개 |

**교훈**: ACM 은 `default_entry` 만으로 판단하지 말 것. 반영 확인은 **로봇 링크와의 쌍별 값**으로 하고,
`False` 는 '항목 없음'과 같은 뜻으로 취급해야 한다. (Stage 5 이래 세 번째 '조용한 무효' 사례.)

## 6. 부록 — 접촉 10건의 진짜 원인: 직선인데 손목이 뒤집히는 Cartesian 해 (2026-07-29)

### 무엇을 봤나

07-28 문서는 접촉 10건의 원인을 '구 영역이 ρ 안 이웃 객체를 통째 허용' 으로 **추정**하고 그것을 다음
과제 1순위로 적었다. 고치기 전에 **접촉 쌍을 기록하도록 계측**부터 넣고(`_invalid_waypoints(pairs=…)`)
같은 열매를 18회 재현했더니 추정이 틀렸다.

| 관측 | 값 |
|---|---|
| 접촉 쌍 | **`rg2_rightfinger \| stem_r0_p2_s0`** — 이웃 열매/화방대가 아니라 **주 줄기** |
| 구 영역이 허용한 객체 | **`rachis_r0_p2_t0` 1개뿐**(= 안전 기준도 허용하는 자기 화방대) |
| 접촉 행의 접근구간 관절 | **5.3 rad** (다른 열매는 0.4 rad 대) · 웨이포인트 84점 |
| 무접촉 행의 접근구간 관절 | **0.65 rad** · 48점 |
| 재현율 | 18회 중 8회 접촉(07-28 은 18회 중 10회) — **같은 열매에서 해가 확률적으로 갈렸다** |

주 줄기는 열매 중심에서 15.4cm 라 ρ=6.5cm 구 밖이다 ⇒ **영역 형상을 좁혀도 이 접촉은 안 준다.**

### 왜 그런 해가 통과했나

`cartesian_to` 가 `jump_threshold = 0.0` 으로 요청하고 있었다 — MoveIt 의 **관절 점프 필터가 꺼진**
설정이다. 그래서 TCP 는 직선을 따라가되(`fraction=1.00`) 손목이 특이점 근처에서 뒤집히는 해가
그대로 '완전직선 성공' 으로 채택됐고, 그 자세에서 오른손가락이 주 줄기를 스쳤다.
`_best_straight_candidate` 도 fraction 만 보고 골랐기 때문에 **더 나은 해가 존재하는데도**
확률적으로 나쁜 쪽을 뽑았다(같은 각도에서 IK 해가 갈린다).

### 수정

- `_jl_of(wp)` — 웨이포인트 열의 관절 경로길이·최대 1스텝 변화.
- `_straight_ok(wp)` — 관절 경로길이가 `approach_jl_max`(기본 **2.0 rad**)를 넘으면
  **'직선 성공' 으로 인정하지 않는다.** `plan_approach` 의 ①(직선 채택)과 ③(부분경로 폴백)에 함께 적용
  — 걸린 경로를 부분경로로 되쓰지 않게 한다.
- `_best_straight_candidate` — 한도를 넘는 후보는 fraction 을 0 으로 낮춰 탈락시킨다.
- MoveIt 자체 필터도 파라미터로 열어 뒀다(`cartesian_jump`, `cartesian_revolute_jump`, 기본 0=끔).
  경로 전체를 보고 **후보를 교체**하는 편이 경로를 중간에서 자르는 것보다 낫다고 보고 기본은 끔.

**⚠ 순위에는 넣지 말 것.** 관절길이를 후보 순위에서 `prefer_near_home` 보다 **앞에** 뒀더니
home 에서 먼 자세가 뽑혀 자유공간 계획이 실패했다(실측: 한 열매가 18/18 폴백, 유효 108 → 90).
거르는 건 **한도 검사**의 몫이고, 순위 기준은 종전대로 두는 게 맞다.

### 효과

| | 07-28 | 07-29 |
|---|---|---|
| 안전 기준 접촉 | 10건 | **0건** |
| `harvest_linear` 유효 | 98/108 | **108/108** |
| `fruit_r0_p2_t0_f1` 접근구간 관절 | 5.31 rad | **0.65 rad** |
| 완전직선 | 108/108 | 108/108 (유지) |

**교훈**: `fraction=1.00` 은 **TCP 가 직선이라는 뜻일 뿐** 관절이 얌전하다는 뜻이 아니다.
Cartesian 결과는 관절 경로길이로 한 번 더 걸러야 한다. 그리고 **접촉 개수만 세는 계측으로는
원인을 못 좁힌다** — 접촉 쌍(무엇과 닿았나)을 같이 남겨야 추정이 아니라 규명이 된다.
